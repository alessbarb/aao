# AAO Runtime Consumer Contract

**Status:** integration contract for the current development API; not an
authorization grant, audit verdict, or production SLA. **API source revision:**
`f929827885048f0373121358c68238b0ad1effeb` (2026-10-19). This is the source
revision described by the contract, not a claim that this document is present
in that commit.

This contract is owned by the runtime team. It describes interfaces other AAO
teams may consume and proposes integration boundaries; it does not change the
runtime, frontend, audit engine, constitution, grants, or promotion policy.
The OpenAPI document generated by the running API and the implementation remain
the executable source of truth. The authorization inventory is
[`PRINCIPAL_AUTHORIZATION_MATRIX.md`](PRINCIPAL_AUTHORIZATION_MATRIX.md).

## Consumer boundaries

| Consumer | Supported interaction | Must not infer |
| --- | --- | --- |
| Control Center / frontend | Read project board and local capabilities using an individual principal with project-scoped `project.read`; render returned states and references. | A listed capability is executable; a proposed or validated patch is applied; an execution is an audit; `IN_REVIEW` is approved. |
| Runtime workers | Use an individual AGENT identity and operation-specific, unexpired project grants. Submit only the fixed registered job contracts accepted by the runtime. | Authentication alone grants project access or execution; client-supplied identity is authoritative. |
| Audit / review service | Use an individual AUDITOR identity and the specific review grant. Read a patch through the auditor-only route while its work is `IN_REVIEW`; bind any report to exact candidate and evidence digests. | A distinct process/model proves independence; a stored review proves valid auditor identity, policy compliance, or promotion authority. |
| PR / conformity controller | Consume immutable candidate identifiers, check results and signed evidence through its own trust policy. Treat runtime records as inputs, not a promotion decision. | Green CI or runtime state authorizes GitHub merge. |

Credentials are bearer secrets and must be transmitted only over the approved
local/secure channel. Never put them in URLs, logs, source, command arguments,
browser storage, or evidence. Credential issuance, rotation, revocation, mandate
administration, project creation and grant administration remain CEO-only
development operations. They are not ordinary worker or frontend APIs.

## Existing runtime interface

All routes below are implemented in `src/aao/work_management_api.py`. JSON
examples are illustrative shapes from the current implementation; clients
should tolerate additive fields and must treat unknown states as non-approved.

### Health and identity

- `GET /health`: service identity and `autonomous_execution` flag. It is not a
  database readiness check.
- `GET /ready`: readiness plus sanitized database availability; no connection
  details or credentials are returned.
- `GET /v1/principals/me`: individual AGENT identity only; returns principal
  ID, kind and enabled state, never credential material.

### Project and work read model

- `GET /v1/projects`: project list. Individual AGENT callers are limited by
  `project.read`; development CEO behavior is distinct and not a frontend
  identity.
- `GET /v1/projects/{project_id}/board`: project-scoped board with work items,
  execution summaries, review records, patch proposal metadata and validation
  summaries. The caller needs project read authorization (see the authorization
  matrix for precise role checks).
- `GET /v1/projects/{project_id}/capabilities`: local registered versions,
  contract/provenance/requirements/evidence metadata and an explicit
  `execution_authorized: false` field. Listing is discovery only.
- `GET /v1/projects/{project_id}/capability-evaluations`: recorded task-level
  reuse/adapt/build comparisons. A recommendation is not authorization or proof
  of use.

The board is a projection over persisted runtime records. Consumers should
preserve distinctions among work status, execution status, patch proposal,
validation, review, and PR lifecycle; no UI-side state transition is canonical.

### Governed capability and execution operations

- `POST /v1/projects/{project_id}/capabilities`: register immutable,
  project-local capability metadata. Requires `work.create`; contract fields,
  tests and evidence references are validated. Result is `registered_local`,
  not executable authorization.
- `POST /v1/projects/{project_id}/capability-evaluations`: persist one
  reuse/adapt/build comparison for a task. The task and selected version must
  belong to the project. Evaluation is a recorded recommendation only.
- `POST /v1/work/{work_id}/stage-repository-check`: stage only the fixed
  `core-unit` repository-check job. Requires `work.admit` and
  `execution.claim`, an active project, READY work, a registered supported
  capability version, and a prior reuse/adapt evaluation for this task. The
  queue feature flag must be enabled. It does not accept arbitrary commands.
- `POST /v1/work/{work_id}/stage-inert`: stage the fixed inert payload under
  equivalent admission/claim conditions.
- Queue claim/completion are internal runtime operations, not public HTTP
  routes. The worker contract and lease checks live in `execution_queue.py`.
  External model, tool and effect execution remains disabled.

### Proposed code changes

- `POST /v1/work/{work_id}/patch-proposals`: an assigned AGENT with
  `code.propose` may persist a bounded diff against a full base SHA. This is a
  proposal only; allowed changed paths and patch constraints are checked by the
  patch proposal module.
- `POST /v1/work/{work_id}/patch-proposals/{proposal_id}/validate`: validates
  the stored patch in a disposable clone and persists the resulting tree hash.
  It does not apply changes to the canonical checkout.
- `GET /v1/work/{work_id}/patch-proposals/{proposal_id}`: auditor-only read of
  the exact patch while work is `IN_REVIEW`, with digest validation and
  author/executor separation checks.

Proposal, isolated validation and application are separate states. There is
currently no API operation that applies a patch to the canonical checkout or
merges a PR. A validation result is not a test-suite result unless its evidence
explicitly says which checks ran against which candidate.

### Review and current fail-closed behavior

- `POST /v1/work/{work_id}/reviews` accepts `APPROVE`, `REJECT` or `VETO` as
  request values, but `APPROVE` is rejected fail-closed while independent
  identity/evidence verification is unavailable. This route is not a substitute
  for GOV-REV-001 audit or conformity.
- Work progression to `DONE` remains disabled pending independent approval
  verification.
- Patch and review endpoints bind operations to exact SHA/digest values where
  specified. Consumers must not reuse a result after candidate bytes or policy
  change.

## Common failure semantics

Clients should use HTTP status and machine-readable response body as returned;
do not infer an undocumented retry is safe.

| Status | Meaning for consumers |
| --- | --- |
| `401` / `403` | Missing, invalid, revoked, wrong-kind identity or required grant. Do not retry with a stronger/shared credential. |
| `404` | Resource not found in the caller's permitted route/context. |
| `409` | State, grant, capability version, duplicate proposal, or authorization changed/conflicts. Refresh authorized read state before deciding next action. |
| `422` | Request violates a bounded contract or schema. Correct the request; do not retry unchanged. |
| `503` | Required runtime feature/configuration/dependency unavailable. Do not claim execution occurred. |

Authorization is checked in the protected transaction for applicable routes;
credential and grant revocation is serialized using row locks in the covered
paths. See the source authorization matrix for route-specific guarantees and
known limits. Do not generalize selected race tests into exhaustive concurrency
proof.

## Integration proposals for consuming teams

These are proposals for interface alignment, not changes to other teams' code:

1. **Frontend:** consume only the project board and capability/evaluation read
   routes; render server-provided IDs, timestamps, statuses, SHA/digests and
   evidence references. Keep CEO administration on its separate authority
   surface. Display missing audit/PR evidence as pending, never as success.
2. **Auditor:** fetch an exact patch only through an authorized AUDITOR
   identity; independently obtain the candidate base/evidence and record report
   SHA, patch digest, candidate tree, policy version, reviewer identity and
   veto/reject decision. The current runtime does not establish auditor
   independence or protected report storage.
3. **Conformity / PR controller:** require exact candidate SHA, current policy
   digest, required check evidence, valid auditor report and no active veto.
   Any candidate update invalidates prior conformity. Keep the promotion
   credential and policy outside implementer-controlled PR execution.
4. **Capability consumers:** treat registry entries as descriptions, not
   permissions. A runtime operation must still check principal kind, project
   grant, task state, capability type/version and its fixed allowlisted contract.

## Explicit non-contracts and unresolved ownership

- No guarantee of independent audit, automatic promotion, merge authorization,
  production identity, continuously available execution, sandboxed arbitrary
  code, or external effects.
- No privilege is inherited from a skill, registered capability, evaluation,
  frontend session or GitHub review state.
- No schema or frontend implementation changes are proposed by this document.
- Downstream teams should propose contract changes through a reviewable change
  to this document and the corresponding runtime/OpenAPI tests; runtime owners
  will assess backward compatibility and authority implications.
